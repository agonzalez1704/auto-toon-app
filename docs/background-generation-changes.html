Auto Toon — background-resumable generation

Generations now survive the user backgrounding the app, locking the device, or quitting and returning later. The bulk of the work was a new SSE protocol that lets the client correlate streamed jobs with persisted server-side records, plus an AppState resume loop that polls those records on foreground and dispatches results to the right screen.

The new SSE job protocol core

The problem

Both video and commercial generation are end-to-end SSE: the server streams progress, eventually emits a success event with the final URL, and the client navigates to a viewer screen. That works perfectly while the app is in the foreground. It breaks the moment iOS suspends the app — the SSE socket dies, the client never sees success, and there's no recovery: the work might be done on the server but the user has no way to learn that, no way to land on the result, and the UI sits frozen on the generating screen until they hard-quit.

The fix in one paragraph

The backend now emits a brand-new SSE event job_started the moment it persists the videoGeneration row, carrying that row's id. The client takes that id and registers it with a central useGenerationTracker zustand store (persisted to AsyncStorage). When the app foregrounds, a useGenerationResume hook polls GET /api/fashion-editorial/video/status/<id> for every tracked id. Any job that reports completed or failed is dispatched through an onComplete handler the source screen registered at mount time, which performs the same navigation it would have on a live SSE success. The result: a video generation that started before the user pulled down on the home indicator finishes its server work, fires a push, and on next foreground the user is dropped straight into the player.

Why a tracker store and not just a screen-local ref

The screen that started the generation may not be mounted by the time the resume polling fires — the user could have navigated away, sent the app to background, swiped through home, killed the app, come back. The persisted tracker survives all of those: the id stays in AsyncStorage; useGenerationResume runs at the root layout (not the screen layout), so it runs even on cold start; and screens re-register their onComplete handler on mount, so whichever screen the user is on when results come back receives the dispatch.

Why push and polling

Push notifications arrive in seconds when the network and APNS cooperate. The push handler in app/_layout.tsx now reads generationId off the payload and calls tracker.completeJob directly — the banner clears instantly without a network round trip, and tapping a notification routes through the same handler that an SSE success would have. Polling is the fallback for when push is slow, dropped, or disabled — there is always exactly one terminal dispatch per job (the tracker checks for the id before dispatching, so push + poll race-safe).

Tracker store — what it actually stores

interface InFlightJob {
  id: string                     // videoGeneration.id today, generation.id later
  kind: 'video' | 'image'
  origin: string                 // 'commercial' | 'video-generator' | …
  startedAt: number
  preview?: string               // e.g. storyboard URL for commercial
  label?: string                 // 'Commercial: Espresso machine'
}

interface GenerationTrackerState {
  jobs: Record<string, InFlightJob>        // persisted
  handlers: Record<string, OnComplete>     // NOT persisted

  registerJob(job)
  updateJob(id, patch)
  completeJob(id, result)                  // calls handler + removes
  removeJob(id)
  registerHandler(origin, handler)         // screen calls this on mount
  unregisterHandler(origin)                // screen calls this on unmount
}

The handlers map is intentionally non-persisted — functions don't survive serialization, and each screen re-registers its handler when it mounts. If the matching screen isn't mounted when a result arrives (e.g. user is somewhere else in the app), the result sits in the registry until polling re-fetches it; tapping the in-flight banner routes the user back to the source screen, the handler registers, and the next poll dispatches.

Caveats / known sharp edges

  • Resume polling currently runs 8 × 3s = 24s per active job per foreground. Long-running jobs that don't complete in that window get re-checked on the next foreground tick. No persistent background timer (iOS would kill it).
  • If the SSE stream fires success while the screen is still mounted, removeJob runs before the resume hook would have caught it — no duplicate dispatch.
  • If a generation row is deleted server-side (rare) the GET status endpoint returns 404 and the job stays stuck in the tracker until the user manually clears it. Could add a stale-job sweep later.
  • The in-flight banner currently only routes back to commercial and video-generator. Add more cases to InFlightBanner.onPress when wiring new origins.
